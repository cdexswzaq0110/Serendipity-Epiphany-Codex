# 工作單

## 何時用／何時不用

在需求要交給另一個人、Agent 或下一個工作階段時使用。探索中的構想不適合；單一明確的一行修正也不必為形式建立工作單。

## 步驟

1. 用結果語言寫「要做的事」，連回核准的產品契約或問題。
2. 將驗收條件編為穩定 ID：`AC1`、`AC2`……；後續即使排序改變也不要重新編號。
3. 每條 AC 附上驗證方式、所需資料與可觀察的通過結果。
4. 列出預計會動的模組與檔案；未知位置可列模組與搜尋入口，不要編造檔名。
5. 明列不做的事，防止實作者自行擴張。
6. 列出前置相依、外部相依、順序限制、寫入衝突與需要誰決策的未決事項。
7. 讓未參與討論的人逐條模擬判定；任何需要猜意圖的 AC 都退回改寫。

## 輸出要回答的問題

- 這張工作單要交付什麼可觀察結果？
- `AC1…ACn` 各自如何驗證與判定？
- 會動哪些模組或檔案，不會做什麼？
- 有哪些相依、順序、衝突與未決事項？
- 另一個人或程式能否不靠原作者解釋逐條驗收？

## 驗證

- AC ID 唯一、穩定、無缺號要求，文字與驗證方式一一對應。
- 每條 AC 的通過結果可由命令、檔案、介面觀察或人工檢查判定。
- 範圍與不做事項能阻止相鄰需求滲入。
- 相依與寫入衝突分開描述。

## 反模式

- 用「完成開發」「確認正常」當驗收條件。
- 把實作步驟當成唯一成果。
- 修改 AC 文字卻沿用舊審查結果。
- 沒寫不做事項，讓工作單變成無限範圍。
