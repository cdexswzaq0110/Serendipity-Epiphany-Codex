# 最小實作

## 何時用／何時不用

在工作單與驗收條件已足夠清楚、要修改程式時使用。需求仍有會造成重做的缺口時先釐清；純研究或只讀審查不用。

## 步驟

1. 讀工作單、驗收條件、專案指令與相關程式；確認分支與工作樹。
2. 先搜尋既有函式、套件、平台能力與相似測試，避免重複實作。
3. 依階梯選最小方案：不用寫 → 已經有 → 標準庫 → 平台原生 → 已裝依賴 → 短小新增 → 最小可動切片。
4. 一次只改完成當前 AC 必要的範圍，保留既有介面與使用者行為。
5. 不交付 stub、placeholder、假資料、空殼函式或把核心工作留成 TODO。
6. 新增或更新能觸及變更行為的測試；執行與風險相稱的測試、lint 或 build。
7. 改了程式後，必須取得該版本的新驗證輸出才能說完成；舊結果、相鄰測試與「應該會過」都不算。
8. 檢查 diff、未追蹤檔與 secrets，清除本輪暫存物，不做無關重構。

## 輸出要回答的問題

- 哪些既有能力被重用，為何仍需要修改？
- 修改了什麼，如何對應工作單與 AC？
- 哪些驗證在修改後實際執行，結果是什麼？
- 有哪些未驗證、風險與刻意不做事項？

## 驗證

- 每條已完成 AC 都有本次版本的可重跑證據。
- 搜尋結果與 diff 顯示沒有平行重造既有能力。
- 交付物可運作，沒有 stub、placeholder 或核心 TODO。
- diff 只包含必要變更，沒有 secrets 與無關檔案。

## 反模式

- 一開始新增框架、抽象層或依賴。
- 為讓測試綠燈而刪除或弱化測試。
- 修改後沿用修改前的測試結果。
- 把「檔案存在」當成功能可運作的證據。
