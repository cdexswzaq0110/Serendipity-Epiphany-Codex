# 技術設計

## 何時用／何時不用

用於多元件、資料模型、外部整合或高回滾成本的變更。小型局部修正且接縫已知時不用；產品契約不清楚時先回上游，不替產品決定需求。

## 步驟

1. 讀產品契約與現況，盤點既有元件、限制、流量、資料與部署邊界。
2. 估算量級並找第一個瓶頸；沒有量級時明示假設，不假裝精確。
3. 定義元件責任、資料流、同步／非同步邊界與失敗傳播。
4. 定義 API 契約、資料模型、不變量、生命週期、遷移與相容策略。
5. 比較至少兩個實際可行方案；記錄取捨、採用理由與未採用原因。
6. 設計錯誤處理、可觀測性、安全、容量、回滾與降級路徑。
7. 將重要且長期有效的決策寫成 ADR，並切出可獨立驗證的垂直切片。
8. 深入檢查資料層、韌性與估算時，讀 `references/` 內對應文件。

## 輸出要回答的問題

- 架構與元件邊界是什麼，資料如何流動？
- API、資料模型與不變量如何定義？
- 容量假設與第一個瓶頸是什麼？
- 選了什麼、放棄什麼，代價為何？
- 如何遷移、相容、觀測、降級與回滾？
- 哪些決策需要 ADR，實作接縫在哪？

## 驗證

- 每個驗收條件都能追到元件或介面。
- 估算單位與假設一致，瓶頸有計算或既有量測依據。
- 資料不變量有資料庫、程式或流程中的明確保護者。
- 回滾不是「還原程式碼」一句話，而包含資料與外部契約。

## 反模式

- 畫圖很多但沒有責任與介面。
- 未量測就為假想規模導入重型架構。
- 只寫理想流程，不寫失敗與回滾。
- 用 ADR 記錄每個小決定，或完全不記不可逆決策。
