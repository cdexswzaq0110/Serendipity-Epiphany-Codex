# 規格審查

## 何時用／何時不用

在有固定驗收條件與待審產物時使用，逐條回答「是否做對要求」。沒有穩定契約時不能假裝審查；不要評論命名、架構、風格或其他工程品質。

## 步驟

1. 固定契約版本與完整 AC 清單，確認沒有缺漏、重複或未知 ID。
2. 只讀檢查產物、diff、測試輸出與文件，必要時執行不改狀態的驗證。
3. 每條 AC 只給一個判定：`pass`、`fail`、`cannot_verify`。
4. `pass` 必須引用可檢查證據，例如本次指令輸出、檔案與位置、或可重現介面結果。
5. `fail` 說明預期、實際與最小差距；不要順手改程式。
6. `cannot_verify` 說明缺少什麼、為何目前不能判定、誰能補足。
7. 所有 AC 都是 pass 才能說規格通過；有 cannot_verify 就交給決策者，不得當成 pass。

## 輸出要回答的問題

- 每個 AC 的判定是 pass、fail 還是 cannot_verify？
- pass 的可檢查證據在哪裡？
- fail 的預期與實際差距是什麼？
- cannot_verify 的原因與所缺證據是什麼？
- 契約是否完整且版本一致？

## 驗證

- 輸出中的 AC 集合與契約完全相同。
- 每個 pass 都能回到具體指令結果或檔案位置。
- cannot_verify 都有原因，沒有用模糊措辭逃避判定。
- 審查期間未修改產物，也沒有混入品質評論。

## 反模式

- 用整體印象一次宣布通過。
- 把測試名稱當證據但沒有本次輸出。
- 把 cannot_verify 當作沒有問題。
- 因程式碼漂亮而忽略做錯需求，或因風格問題判 AC fail。
