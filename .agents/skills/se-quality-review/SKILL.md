# 品質審查

## 何時用／何時不用

只在規格審查全部 pass 後使用，回答「做得好不好、是否安全維護」。若任何 AC fail 或 cannot_verify，先停止；不要重新審規格或直接修正程式。

## 步驟

1. 取得待審產物、diff 摘要、指紋、驗證結果與品質準則；不要參照規格審查者的文字。
2. 讀變更與必要上下文，檢查正確性風險、安全、資料完整性、相容性、錯誤處理、效能與可維護性。
3. 使用 `references/smell-baseline.md` 校準常見 smell，但只回報能指向具體位置與後果者。
4. 每個發現標示嚴重度：高＝可能造成錯誤、安全事故或不可安全交付；中＝明顯維護或可靠性風險；低＝有限影響的改善。
5. 每個發現包含位置、理由、觸發條件與最小改進方向；證據不足就降低確定性或不報。
6. 明確說明是否有高嚴重度發現；沒有發現不等於證明完美。

## 輸出要回答的問題

- 有哪些高／中／低嚴重度發現？
- 每個發現的位置、理由與實際後果是什麼？
- 在什麼條件下會觸發，最小改進方向為何？
- 是否存在阻止安全交付的高嚴重度問題？

## 驗證

- 已確認規格審查全部 pass 才開始。
- 每個發現都有可導航的位置與具體理由。
- 嚴重度依後果而非個人風格決定。
- 沒有把偏好、未證實猜測或規格缺漏包裝成品質 finding。

## 完整做法

code smell 基線：讀 [references/smell-baseline.md](references/smell-baseline.md)。finding 格式與彙整流程在 `se-spec-review` 的完整做法裡。

## 反模式

- 規格未過就花成本做品質審查。
- 只列「可讀性不好」而無位置與後果。
- 把所有問題標高，或只挑格式與命名。
- 一邊審查一邊修改，使證據版本失效。
