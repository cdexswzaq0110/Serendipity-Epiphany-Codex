# 問題定義

## 何時用／何時不用

用於把構想收斂成可驗證的問題，或發現團隊對使用者、範圍與成功的理解不同時。若問題與範圍已由有效契約明確固定，直接做可行性或產品契約；不要用來設計架構或實作。

## 步驟

1. 用一句話寫出目前痛點、受影響的人與可觀察後果；先查可取得的事實，不把調查丟回使用者。
2. 指定主要使用者、使用情境、現行替代方案與最痛的摩擦。
3. 分開列出「要做」與「不做」，並標示任何會造成重做的邊界缺口。
4. 定義能量測的成功指標、基線、目標值與觀察期間；未知就標未知。
5. 列出假設、證據狀態、假設失敗時的影響與最小驗證方法。
6. 只提出會改變產出的問題；先問錯了會重做的問題，每輪不超過三個需要人決策的問題。
7. 讓使用者確認問題與範圍，再交給可行性或產品契約。

## 輸出要回答的問題

- 真正要解的問題是什麼，證據是什麼？
- 誰在什麼情境受到影響，現行替代方案是什麼？
- 這一輪做什麼、不做什麼？
- 成功如何量測，基線與目標是什麼？
- 哪些是假設、未知與待使用者回答的問題？

## 驗證

- 問題陳述描述結果而非預設解法。
- 每個成功指標都有可觀察的量測方法。
- 範圍同時包含做與不做，且關鍵假設沒有偽裝成事實。
- 每個問題都能指出不同答案會改變哪一段產出。

## 反模式

- 先選技術再倒推問題。
- 把「提升體驗」當成不可量測的成功標準。
- 問使用者可以從程式庫或環境查到的事實。
- 為了完整而一次盤問大量不影響決策的問題。
