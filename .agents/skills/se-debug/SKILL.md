# 除錯

## 何時用／何時不用

在有 bug、測試失敗、間歇性錯誤或結果不符預期時使用。需求本身不明確時先釐清；沒有失敗訊號時不要以大規模重構假裝除錯。

## 步驟

1. 建立最小可重現案例，記錄環境、輸入、預期、實際與穩定重現方式。
2. 先做一個在修正前會紅的回饋迴圈；間歇問題先量測頻率與時間線。
3. 從觀察提出可反證假設，為每個假設寫出預測與量測方法。
4. 一次只改一個變因，保留結果；先縮小邊界，再讀最可能的程式路徑。
5. 找到根因後做最小修正，不用症狀補丁掩蓋資料或狀態問題。
6. 重跑原重現案例、相鄰回歸測試與必要整體測試。
7. 確認修正沒有改變契約外行為；記錄根因、證據與尚未驗證處。
8. 同一錯誤連續修正三輪仍失敗就停止嘗試，先**補外部訊號**（見下）再回到步驟 3；補完仍無法區分，回報證據與下一個可區分假設。

## 補外部訊號：只讀不改的一段

用同樣的資訊再試一次不是重試，是同一次呼叫。第三輪還在原地時，缺的通常是這個程式庫以外的事實。

只讀不改，依序看：官方文件的那一節 → 本機實際安裝的依賴原始碼（不是記憶中的 API）→ 使用同一套依賴的參考專案。讀完先輸出三行，才回到步驟 3：

```text
根因候選：<機制，可反證>【推論】
選項：<A／B，各自放棄什麼>
下一步：<回到哪一步，要驗哪個可觀察量>
```

沒有這三行就不算補完；讀了一輪但假設沒變，等於沒讀。只讀的查找可以平行交出去；需要乾淨的上下文才讀得下去時，另開獨立的工作階段。

## 輸出要回答的問題

- 如何穩定重現，修正前的失敗證據是什麼？
- 測了哪些假設，每次量測排除了什麼？
- 根因與症狀之間的因果鏈是什麼？
- 最小修正是什麼，回歸驗證結果如何？
- 還有哪些未驗證或間歇風險？

## 驗證

- 原案例在修正前失敗、修正後通過。
- 每次實驗只改一個變因，結果可追溯。
- 相鄰回歸測試在同一版本通過。
- 根因說明能預測觀察到的症狀，不只是相關性。

## 完整做法

原 v1 的完整流程（紅→縮→猜→測→修→綠、三次修不好的處理）：讀 [references/v1-debug.md](references/v1-debug.md)。

## 反模式

- 同時改多處，成功後不知道哪個變因有效。
- 沒重現就憑直覺修正。
- 只重跑變綠的單一測試，不查回歸。
- 用 retry、sleep 或寬鬆例外處理掩蓋未知根因。
- 卡住就換個寫法再試一次：資訊沒變，結果的分布就沒變，先補外部訊號。
