# 產品契約

## 何時用／何時不用

在問題與可行性足夠清楚、需要讓產品與工程對「完成」有相同判準時使用。若問題仍未定義，先做問題定義；不要在此指定內部架構或程式碼品質偏好。

## 步驟

1. 將目標拆成少量使用者故事：誰、在什麼情境、要完成什麼、得到什麼價值。
2. 畫出主要 UX 流程，包含入口、成功、失敗、空狀態、取消與恢復。
3. 為每個故事寫可獨立判定的驗收條件：給定狀態、操作、可觀察結果。
4. 避免「正確」「友善」「快速」等無門檻詞；需要時補數值、樣本或判定規則。
5. 定義必要的非功能需求：效能、可用性、安全、隱私、相容性、可存取性與可觀測性；只保留會影響本輪設計者。
6. 列出範圍外、相依、假設與未決問題，指定誰決定。
7. 逐條走查驗收條件，確認另一個人或程式能在不猜意圖的情況下判定。

## 輸出要回答的問題

- 哪些使用者故事構成本輪價值？
- 使用者從入口到成功、失敗與恢復如何走？
- 每條驗收條件如何被觀察與判定？
- 哪些非功能需求會改變方案？
- 範圍外、相依、假設與未決事項是什麼？

## 驗證

- 每個故事至少有一條可檢查的驗收條件。
- 每條條件只有一個清楚結果，且不依賴「看起來合理」。
- UX 的失敗與空狀態沒有被 happy path 吞掉。
- 非功能需求有門檻或明確判定方式。

## 反模式

- 把實作任務當使用者故事。
- 驗收條件重述需求但無法執行檢查。
- 在契約中偷渡尚未決定的技術方案。
- 一開始窮舉所有邊界，讓 MVP 無法前進。
